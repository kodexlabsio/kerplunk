# Inputs and How Lineage Works

| Input | What Konstruct reads | Status |
|-------|---------------------|--------|
| **dbt** | `target/manifest.json` and `catalog.json`: models, seeds, snapshots, sources, tests (attached to columns), `primary_key` constraints, exposures, descriptions, column types. Compiled SQL for lineage; `ref()` and `source()` are resolved from the manifest when only raw SQL is available | v0 |
| **SQL** | Column-level lineage with [sqlglot](https://github.com/tobymao/sqlglot) for dbt models, warehouse views, Airflow SQL and standalone `.sql` files (`CREATE ... AS`, `INSERT ... SELECT`, `MERGE`, `UPDATE`, `DELETE`, `COPY`). Dialect from the dbt adapter or configuration | v0 |
| **Airflow** | DAG files parsed statically (never imported): `with DAG`, assigned DAGs, `@dag`, TaskFlow, TaskGroups, `>>`, `<<`, `chain`, `cross_downstream`. Per task: dbt commands (BashOperator, `@task.bash`, Cosmos, dbt operators) resolved to models with dbt's selection syntax; SQL inline or from files; target and source tables; inlet and outlet assets | v0 |
| **DuckDB** | Tables, views, columns, types, comments, primary keys and view definitions, read only | v0 |
| **Postgres** | Tables, views, materialised views, partitioned tables, columns, types, comments, primary keys and view definitions, read only | v0 |
| **Iceberg** | Any PyIceberg catalog, REST included: namespaces, tables, columns (nested struct fields as `parent.child`), field ids, identifier fields, partitioning, current snapshot. Metadata only; no data files are read | v0 |
| **Dagster** | Definition files parsed statically (never imported): `@asset`, `@multi_asset` and `@dbt_assets` (with its dbt selection), keys and prefixes, dependencies from parameters, `ins=` and `deps=`, groups, asset jobs with their selections, and schedules. An asset's data is the dbt model, warehouse table or SQL target of the same name, and SQL an asset runs gets column lineage. Op-based jobs: `@op`, `@graph` and `@job` (nested graphs, `.alias()`, fan-in, `.map()`/`.collect()`, `graph.to_job()`), one task per op invocation named by its Dagster handle, with column lineage from each op's SQL and dbt runs from `dbt.cli([...])`. `@schedule` and sensors (`@sensor`, `@asset_sensor`, `@multi_asset_sensor`, `@run_status_sensor`, `@run_failure_sensor`): an asset sensor orders its job after the asset, a success sensor after the monitored job | v0 |
| **PySpark** | Python jobs parsed statically (never imported): files that import PySpark, Databricks notebooks exported as source, and files that call `spark.sql`. Each SQL string passed to `.sql(...)` on a Spark session (an object whose name ends in `spark` or `session`, or only `spark` in a file that uses Snowpark) is analysed in the Spark dialect (`[spark] dialect`), so `CREATE TABLE ... AS`, `INSERT INTO` and `INSERT OVERWRITE` give the tables they write column lineage; `spark_catalog.` is the session's own catalogue and is left out of names. A string is read when it is a literal, an f-string without placeholders, a concatenation of literals or a module-level name bound once; SQL built at run time, or formatted with keyword arguments, is a warning | v0 |
| **Looker** | LookML files (`*.lkml`), parsed with the `lkml` parser and never run, with views resolved across files: a refinement (`view: +orders`) adds to its view, a view that `extends` others takes their table and fields, and an abstract view (`extension: required`) is a base only. Each view is an exposure: a view over a table (`sql_table_name`, or the view's own name) reads that table, and each field reads the columns its SQL names as `${TABLE}.column` (in `sql`, `sql_start`, `sql_end`, `sql_latitude`, `sql_longitude`), directly or through the view's other fields (`${field}`, `${view.field}`, a dimension group's `${created_date}`) and the fields a measure filters on, so `impact` on a column reaches the Looker fields built on it and no others. A view over a derived table reads the tables its SQL reads. A table name built with Liquid or parameters, a native derived table, and a field reading a column the table does not have are warnings | v0 |
| **Business definitions** | `definitions.yml` files: each term's name, kind (entity, measure or term), synonyms, definition, owner, status (draft, agreed, approved, retired), approval date, grain, bound columns, required filters, unit, currency, related terms and exceptions. Terms become `term` nodes with `defines` edges to their columns, and the build warns when a bound column or filter column no longer exists (see [Business Definitions](../guide/definitions.md)) | v0 |
| **Apache Ossie** | `*.ossie.yaml` semantic models (0.1.1 and the 0.2.0 draft): each metric becomes a business term of kind `measure` bound to the source columns it reads, primary keys mark entity keys and relationships link entities; anything that does not resolve is a build warning (see [Apache Ossie Models](../guide/ossie.md)) | v0 |
| **Snowflake** | Tables, views, columns, types, comments and view definitions from each database's `information_schema`, through `konstruct[snowflake]` | v0 |
| **BigQuery** | Datasets, tables, views and view queries through the client API, with nested `RECORD` fields and their descriptions, through `konstruct[bigquery]` | v0 |
| **Databricks** | Unity Catalog `information_schema` for each catalogue, including struct columns, through `konstruct[databricks]` | v0 |
| **Trino** | Tables, views, columns, types (with `row` fields as `parent.child`), view definitions and column comments from each catalogue's `information_schema`, and table comments from `system.metadata.table_comments` when the user may read it, through `konstruct[trino]`; Starburst too. SQL is read in the Trino dialect | v0 |

## Several Repositories

`repositories` in `konstruct.toml` lists other repositories to build into the same graph, such as a marketing dbt project that reads tables a finance repository builds:

```toml
repositories = ["../marketing", "../platform/airflow"]
```

Each repository is built with its own configuration (its own `konstruct.toml`, if it has one), under the options of the build that lists it: `--no-dbt`, `--no-warehouse` and `--dialect` apply to every repository. Its analyses are cached under `konstruct-out/repositories/<name>/` of the repository that lists it; the name is the folder's, with its parent's added when two folders share one (`b-analytics`). Konstruct writes nothing to the other repositories, though dbt writes its usual `target/` there when it runs. The repositories a listed repository lists in turn are not followed.

A relation two repositories share is one node, and a model one repository builds that another reads as a dbt source is linked column by column, so `impact` and `trace` cross from one repository to the next. A business term in one repository's `definitions.yml` can name a column another repository builds, so the finance and marketing repositories share one definition of revenue; a term defined in more than one repository is a build warning. Each repository's SQL is analysed before the graphs are merged, so a `SELECT *` over a relation another repository builds is not expanded (a build warning says so); columns the SQL names are linked. Two different things with the same id, such as two dbt packages both called `shop` with a model `stg` in different schemas, stay apart: the later repository's keeps its id with `@<name>` added (`model.shop.stg@marketing`). Nodes from another repository carry its name in `repository` and their paths relative to this one, the build watches their files for `--update` and `konstruct status`, `konstruct status` lists what it finds in each repository, and their warnings are prefixed with the repository's name.

## How Lineage Works

- Konstruct qualifies each statement against the columns it knows (from the dbt catalog, the warehouse, or the lineage of upstream models, processed in dependency order), so `SELECT *` expands. sqlglot then follows every output column through CTEs, subqueries, aliases, unions and window functions to physical columns.
- A path made only of column references and renames is `direct`; anything else (arithmetic, functions, aggregates, `CASE`, window functions) is `transformed`.
- Columns that change which rows a model returns, without being selected (join keys, filters, GROUP BY, HAVING, QUALIFY), are recorded as `feeds` edges with `role: reference`, traced through CTEs. Impact reports the relations that use them but does not then mark every downstream column, which would bury the answer.
- Nested data is followed: `o.customer.address.city`, `customer['country']`, `items[1].sku`, `unnest(items)` and `FROM t, UNNEST(t.items) AS i` with `i.sku` trace to the nested column (`orders.items.sku`), in outputs and in conditions, through CTEs; reading a field or unnesting a list counts as a direct pass-through. Struct columns, and the structs inside lists and map values, are listed field by field for every engine, named the way SQL reads them.
- Without compiled SQL, dbt models are rendered by Konstruct in a sandbox: loops, variables, `ref`, `source`, `config`, the project's and packages' macros (`dbt_utils.*`), `adapter.dispatch` and dbt's cross-database macros (`dbt.date_trunc`, `dbt.cast`, `dbt.concat`, `dbt.hash`, `dbt.date_spine` and others). An unknown macro becomes a function call that keeps its arguments, so the columns passed to it stay in the lineage.
- dbt models, warehouse tables with the same relation name, Airflow SQL targets and Iceberg tables merge into one node, so lineage crosses tools: a column computed in dbt, copied into a reporting table by an Airflow task, and used by a dashboard is one chain.
