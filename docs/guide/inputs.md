| **Loaders** | The tables ingestion tools land, from the marks each leaves in the warehouse: metadata columns, bookkeeping tables or a schema of its own (see [Loaders](#loaders)). Landed tables are roots: they count towards no lineage coverage, their formulas stop there, and, fed by their sync task, they are not orphans in REPORT.md | v0 |
| **Loader configuration** | The files that configure loaders, read without running them: dlt pipelines (parsed with `ast`) and exported dlt schemas, `meltano.yml`, Singer catalogs and state files, Airbyte connections (Octavia, API exports and Terraform), Fivetran's Terraform resources, Debezium and other Kafka Connect connectors, Estuary catalogs, Sling replications, Lakeflow Connect bundles and AWS DMS table mappings (see [Loader configuration](#loader-configuration)). | **Fivetran lineage** | When a warehouse holds the Fivetran Platform Connector's lineage tables (`source_schema`, `source_table`, `source_column`, `destination_*`, `table_lineage` and `column_lineage`, in `fivetran_log` or `fivetran_metadata`), each connection's source tables and columns are added, outside the warehouse and named in full after the connection (`salesforce_prod.Salesforce.Account`), with column lineage into the tables it lands in that warehouse, so `trace` reaches the source system while short names such as `account.name` keep meaning the landed table. The warehouse's own destination is the only one the log describes, or else the one that lands the lineage schema; the other destinations of the account are left out, and so are tables and schemas deleted from the source. Both the current `connection` table and the older `connector` are read, and an unreadable lineage schema, or one whose destination is not clear, is a warning. `[fivetran] lineage = false` turns the queries off | v0 |
| **dlt lineage** | From each dataset's `_dlt_version` table, the newest version of each schema dlt loaded into it, read with one query: each table's resource, as a source table outside the warehouse (`dlt.github.issues`) feeding the dataset's dlt sync task, with the table as evidence; nested tables and dlt's own are left out. | **Business definitions** | `definitions.yml` files: each term's name, kind (entity, measure or term), synonyms, definition, owner, status (draft, agreed, approved, retired), approval date, grain, bound columns, required filters, unit, currency, related terms and exceptions. | **Vocabularies** | SKOS concepts and OWL classes in Turtle, N-Triples or RDF/XML files named in `[vocabularies] paths`, read as business terms with their labels, definitions and broader concepts, through `konstruct[rdf]` (see [Business Definitions](../guide/definitions.md#vocabularies)) | v0 |
| **Apache Ossie** | `*.ossie.yaml` semantic models (0.1.1 and the 0.2.0 draft): each metric becomes a business term of kind `measure` bound to the source columns it reads, primary keys mark entity keys and relationships link entities; anything that does not resolve is a build warning (see [Apache Ossie Models](../guide/ossie.md)) | v0 |

## Loaders

Konstruct recognises a loader's tables only by the full set of marks the loader documents, so an application's own `op`, `deleted` or `received_at` column, or a `tracks` table of its own, is not taken for a loader's. A mark that several tools share names the family (`singer`, `segment_spec`); a companion table that only one of them leaves in the same schema refines it, and so does a loader the project names for the table in a dbt source's `loader:`. A dbt source whose `loader:` names a tool, with no mark in the warehouse or no warehouse at all, is that tool's landed table all the same, under the name in lower case with words joined by `_` (`Fivetran` is `fivetran`).

| Loader | `loaded_by` | What marks its tables in the warehouse |
|--------|-------------|----------------------------------------|
| Fivetran | `fivetran` | `_fivetran_synced` |

| Singer (Meltano, PipelineWise and other Singer targets) | `singer` | `_sdc_received_at`, `_sdc_batched_at`, `_sdc_sequence` and `_sdc_table_version`, or `_sdc_extracted_at`, `_sdc_batched_at` and `_sdc_deleted_at` |

## Loader Configuration

Discovery reads a file only when its name and a look at its text show one of these formats, so other Python, YAML and JSON files cost one read and are left alone; files over 2 MB are not read. Nothing is imported, run or connected to. A file Konstruct cannot read, such as one nested too deeply or with a value of the wrong shape, is a warning, and the build goes on without it. Every YAML file Konstruct reads, these and the dbt projects, profiles, definitions, Ossie files and ontology packs, cannot be read when its aliases would add more than a million values once expanded, or when it holds a value YAML cannot give, such as a date that does not exist, an integer of more than 4,300 digits or an escaped lone surrogate; a dbt project, profile, definitions, Ossie or pack file cannot be read either when it is neither UTF-8 nor UTF-16. A table name filled in when the loader runs (`$VAR`, `${VAR}`, a Terraform expression) is a warning too, and that table's lineage is left out rather than read as a name.

A file's tables refine what the warehouse shows: Singer columns on a table `meltano.yml` lands make it Meltano's. When the warehouse already has the loader's sync task for a landed table, the file's source tables feed that task, which records the file in `path` and the pipeline in `pipeline`; otherwise the task is the pipeline's own (`task.dlt.shop`). Each edge from a file carries it as `evidence` (`pipelines/shop.py:4`). A file listed in `[ingestion] paths` adds a table the warehouse does not have, or every table when there is no warehouse, as an inferred table. A file that discovery found reaches only the tables the warehouse, dbt or SQL already show, since an application's own file can look like a loader's; list a file in `[ingestion] paths` to add the tables it lands. A column the file names is linked to the source system's column of the same name when the landed table has it, or when Konstruct knows no columns of the landed table.

## Several Repositories

`repositories` in `konstruct.toml` lists other repositories to build into the same graph, such as a marketing dbt project that reads tables a finance repository builds:

```toml
repositories = ["../marketing", "../platform/airflow"]
```

Each repository is built with its own configuration (its own `konstruct.toml`, if it has one), under the options of the build that lists it: `--no-dbt`, `--no-warehouse` and `--dialect` apply to every repository. Its analyses are cached under `konstruct-out/repositories/<name>/` of the repository that lists it; the name is the folder's, with its parent's added when two folders share one (`b-analytics`). Konstruct writes nothing to the other repositories, though dbt writes its usual `target/` there when it runs. The repositories a listed repository lists in turn are not followed.

A relation two repositories share is one node, and a model one repository builds that another reads as a dbt source is linked column by column, so `impact` and `trace` cross from one repository to the next. A business term in one repository's `definitions.yml` can name a column another repository builds, so the finance and marketing repositories share one definition of revenue; a term defined in more than one repository is a build warning. Each repository's SQL is analysed before the graphs are merged, so a `SELECT *` over a relation another repository builds is not expanded (a build warning says so); columns the SQL names are linked. Two different things with the same id, such as two dbt packages both called `shop` with a model `stg` in different schemas, stay apart: the later repository's keeps its id with `@<name>` added (`model.shop.stg@marketing`). Nodes from another repository carry its name in `repository` and their paths relative to this one, the build watches their files for `--update` and `konstruct status`, `konstruct status` lists what it finds in each repository, and their warnings are prefixed with the repository's name.

## How Lineage Works

- Konstruct qualifies each statement against the columns it knows (from the dbt catalog, the warehouse, or the lineage of upstream models, processed in dependency order), so `SELECT *` expands. A relation whose columns only queries that read it, or its YAML, name is not taken to have only those. sqlglot then follows every output column through CTEs, subqueries, aliases, unions and window functions to physical columns.
- A path made only of column references and renames is `direct`; anything else (arithmetic, functions, aggregates, `CASE`, window functions) is `transformed`.
- Columns that change which rows a model returns, without being selected (join keys, filters, GROUP BY, HAVING, QUALIFY, DISTINCT and DISTINCT ON, the columns a UNION without ALL, an INTERSECT or an EXCEPT compares, and the ORDER BY of a LIMIT), are recorded as `feeds` edges with `role: reference`, traced through CTEs. Impact reports the relations that use them but does not then mark every downstream column, which would bury the answer.
- Nested data is followed: `o.customer.address.city`, `customer['country']`, `items[1].sku`, `unnest(items)` and `FROM t, UNNEST(t.items) AS i` with `i.sku` trace to the nested column (`orders.items.sku`), in outputs and in conditions, through CTEs; reading a field or unnesting a list counts as a direct pass-through. Struct columns, and the structs inside lists and map values, are listed field by field for every engine, named the way SQL reads them.
- Without compiled SQL, dbt models are rendered by Konstruct in a sandbox: loops, variables, `var()` with the values `vars` in `dbt_project.yml` gives the project's models (the global ones, with the block under the project's name over them; a package's macros called from a model see the same), `ref`, `source`, `config`, the project's and packages' macros (`dbt_utils.*`), `adapter.dispatch` and dbt's cross-database macros (`dbt.date_trunc`, `dbt.cast`, `dbt.concat`, `dbt.hash`, `dbt.date_spine` and others). An unknown macro becomes a function call that keeps its arguments, so the columns passed to it stay in the lineage.
- `var()` reads only the project's `dbt_project.yml`: a package's own `dbt_project.yml` vars and values passed with `dbt --vars` are not seen, and a value that is itself a template (`"{{ env_var('START_DATE') }}"`) is unknown, so the call's default is used. Build the project with dbt, so its compiled SQL is read, where those values change the lineage.
- dbt models, warehouse tables with the same relation name, Airflow SQL targets and Iceberg tables merge into one node, so lineage crosses tools: a column computed in dbt, copied into a reporting table by an Airflow task, and used by a dashboard is one chain.
