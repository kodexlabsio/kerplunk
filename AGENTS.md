# Konstruct

An ontology of a business derived from its data stack (dbt, SQL, Airflow, Dagster, Spark, Looker and
Power BI), with the column-level lineage beneath it checked against the warehouse and each change
checked before it merges, by Kodex Labs, MIT licensed. Konstruct reads a data repository and its
warehouse and builds a graph (`konstruct-out/graph.json`, `REPORT.md`, `graph.html` and
`ontology.yml`) that people and coding agents query from a CLI, a Python API, an MCP server, a GitHub
Action and a single offline HTML page.

- `README.md` is the overview; the full documentation is in `docs/` (Sphinx, published to
  https://kodexlabsio.github.io/konstruct/).
- `../kodexlabs.io/DESIGN.md` is the design system the viewer and the docs theme follow.

## Commands

The root `Makefile` runs these by name (`make` lists its targets): `install`, `build`, `format`,
`format-check`, `lint`, `lint-fix`, `test`, `docs`, `paper`, `bench`, and `check` (format-check,
lint and test). A target that runs several tools runs them all and fails if any failed.

- `uv sync` then `uv run pre-commit install`: set up.
- `uv run pytest`: the tests. `eval "$(.kodex/scripts/services.sh up)"` first for Postgres,
  Iceberg REST and the BigQuery emulator; `uv run pytest --cov` must stay at or above 90%.
- `uv run ruff check`, `uv run ruff format`, `uv run mypy`: lint, format and type check (strict).
- `KONSTRUCT_UPDATE_GOLDEN=1 uv run pytest tests/test_golden.py tests/test_interfaces.py`:
  regenerate the golden CLI output, REPORT.md and the interface snapshots, then review the diff.
- `uv run python .kodex/scripts/compat_snapshot.py --ref vX.Y.Z`: add a tagged release to the
  compatibility corpus, in the batch after it is released.
- `pnpm install && pnpm check && pnpm test && pnpm build`, at the repository root, where
  `package.json` is: the viewer. Commit the rebuilt `konstruct/outputs/viewer.html` with the
  source; CI fails if they differ.
- `uv run --group docs sphinx-build -W -b html docs docs/_build/html`: the documentation. Warnings
  are errors, as in CI.
- `uv run .kodex/scripts/benchmark.py 500`: before and after changes to the build, SQL analysis
  or formulas.
- `cargo fmt --check`, `cargo clippy --all-targets --all-features -- -D warnings` and
  `cargo test`, at the repository root: the Rust core. CI also checks it with Rust 1.95, its
  `rust-version`. `uv sync` and `uv run` rebuild the extension after a change under
  `src/`, so the Python tests run against it.
- `uv run python paper/generate.py`, then `cd paper && latexmk -pdf konstruct.tex`: the paper.
  Every measurement of Konstruct in it is a macro from `paper/generated/`, which CI generates and
  git ignores; never type a result by hand. `tests/test_paper.py` fails on a number outside a
  sentence that cites its source, and on a command, MCP tool or export format the paper misses.

Run the tests, ruff, mypy and, for viewer changes, `pnpm check` and `pnpm test`, and for Rust
changes `cargo fmt --check`, Clippy with `-D warnings` and `cargo test`, before finishing a
change; `make check` runs all of them.

## Rules

- **One implementation per component, never a fallback.** Code written in Rust or assembly has no
  Python, Rust or other twin: when a component moves to Rust its Python version is deleted, and an
  assembly routine has no Rust version. Konstruct supports every modern architecture (x86_64,
  aarch64, riscv64, ppc64le, s390x and loongarch64), each with its own assembly, and fails to
  build anywhere else rather than falling back.
- **Never import or execute user code.** DAG and Dagster files are parsed with `ast`; dbt Jinja is
  rendered in a sandbox. Only `konstruct verify` runs a model's SQL, and never commits anything to
  the warehouse.
- **Never break users.** graph.json, the `--json` output, the MCP tools, the CLI's commands,
  options and exit statuses, the Python API and the `konstruct.toml` keys are interfaces. Add to
  them freely; a removal, a rename or a change of meaning is a breaking change, marked with both
  `!` after the type and a `BREAKING CHANGE:` footer. A JSON document's `format_version` changes
  only then, and readers accept every earlier format. `tests/test_interfaces.py` and the corpus in
  `tests/compat/` check this, and the commit check refuses an unmarked removal.
- **Good taste.** Prefer the data structure that makes a special case disappear to the code that
  handles it, and deleting code to adding it.
- **Numbers before claims.** A claim about performance comes with a measurement that anyone can
  repeat, committed with the change (`.kodex/scripts/benchmark.py`, `tests/test_scale.py`, or the
  numbers in `docs/performance.md` with the command that produced them).
- **Every claim about lineage is tested.** A lineage fix comes with a small failing case (usually
  in `tests/test_sql.py`). Changes to what Konstruct claims should hold under `konstruct verify`.
- **The README and the docs say what a user would notice**: a new command, option, input,
  limitation or number. The detailed reference is in `docs/`; keep the README an overview.
- **No peripheral information in the README or docs.** Describe what Konstruct does and how to use
  it. Do not write how a feature was tested or what it has not been tested against (stubs,
  emulators, "not yet run against a real ..."), when a fact was checked, notes about how the work
  was done, or caveats that do not change what a reader does. Test details belong in the tests
  and, for contributors, the test table on the development page.
- **The name** is Konstruct in prose, page headings and UI, and `konstruct` where it is typed: the
  command, package, file names (`konstruct.toml`, `konstruct-out/`), URLs, environment variables
  (`KONSTRUCT_*`), the `--version` output and the `konstruct:` prefix on progress messages.
- **No business material in the repository.** Do not write business, market, fundraising or pricing
  material into this repository, its pull requests or its commit messages. The commit-message
  check rejects the common words.
- **Do not publish** to PyPI, or post anywhere outside this repository, without Dom's go-ahead.
- **Do not name any Kodex Labs client** in code, docs, tests, examples or commit messages, and
  keep Kodex Labs delivery material (engagement plans, pricing, evaluation harnesses, client
  publishers) out of this repository.

## Commits and Releases

- Conventional Commits with the scopes in `.kodex/scripts/check_commit_message.py`, sentence-case
  subjects, lines of at most 100 characters and no AI attribution of any kind. Hooks check this.
- Commits are signed through 1Password. If signing fails with "failed to fill whole buffer",
  1Password is locked: ask for it to be unlocked. Never bypass signing.
- main is protected: changes arrive through pull requests, and nothing pushes to main. Changes
  accumulate on a branch as separate commits and merge in batches, about once an hour, by rebase,
  so each commit stays on main. The batch's last commit runs `.kodex/scripts/prepare_release.py`
  (after rebasing on main), which sets the next version and changelog from every releasable commit
  since the last tag; once it is merged and CI passes, `.github/workflows/release.yml` tags and
  publishes that version. A batch's pull request title is plain words, not a Conventional Commits
  header: CI counts a header title as a commit, as a squash merge would make it one.
  Releasable changes merged without it are released by the workflow from a commit above main.
  While the version is 0.x a release is a patch; only a breaking change (`feat!:` or a
  `BREAKING CHANGE:` footer) gives the next minor. Do not write a body line that starts with
  "BREAKING CHANGE" unless the change is breaking, and never move the version to 1.0: the owner
  decides that.

## Writing Style

- British English (organisation, behaviour, licence as a noun).
- A neutral, technical tone; concise and precise. No emojis anywhere, no em dashes or en dashes.
- The README's opening (the tagline, the first paragraphs and the sections before Why Konstruct)
  and the GitHub description may sell: a category, the problem, why Konstruct is different.
  Claims about Konstruct must be checkable against the code, the tests or the evidence table. A
  third-party figure links its primary source, gives its year, says when it is a vendor survey or
  a prediction, keeps the source's meaning, and is never presented as a Konstruct result or
  saving. No business or funding material, as above. The documentation stays neutral and
  technical.
- `MANIFESTO.md` may state beliefs and commitments; every factual claim and every commitment in it
  must be true of the code and checkable. The paper stays neutral and technical, and its
  third-party figures follow the rules above.
- Comments explain why, not what. Docstrings describe intent and appear in the API reference.

## Formatting

- Python: ruff, single quotes (docstrings double), lines of 110, four-space indents.
- Viewer: Prettier with the kodexlabs.io settings (`.prettierrc`): single quotes, trailing
  commas, lines of 110, four-space indents (two for JSON and YAML), organised imports.

## Dependencies and Pins

Check each when updating packages, and remove it once it is no longer needed.

- **sqlglot `<31`**: a major release changes AST shapes and lineage; raise the bound deliberately,
  with the golden files and `.kodex/scripts/benchmark.py` before and after.
- **mcp `<3`**: the protocol SDK's majors change the server API; raise it with `tests/test_mcp.py`.
- **TypeScript 6** in `package.json`: svelte-check supports `<7`.
- **fakesnow** is not a dev dependency: it pins an old sqlglot. The Snowflake test runs in its own
  CI job with `uv run --with fakesnow --with "snowflake-connector-python<5"`.
- **pnpm 12 lock file** is several YAML documents, so `check-yaml` runs with
  `--allow-multiple-documents`.
- **Dependabot viewer updates** can change the built page; rebuild and commit it before merging.
- **The package layout** is `konstruct/` at the root, with subpackages, built by maturin with
  `python-source = "."` and the extension at `konstruct._core` from the crate at the repository root.
- **PyO3 0.30**: every 0.x minor is a breaking release that changes the binding API; raise it
  deliberately, with `cargo test` and the full suite.
- **maturin `>=1.16,<2`** in `[build-system]`: the build backend; a major can change how
  `[tool.maturin]` is read and what the wheel holds. Raise it with `uv build` and the wheels job.
